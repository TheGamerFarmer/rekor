Guide équipe — Rekor

Monorepo · Node.js + Angular + Flutter · GitHub Actions CI/CD

🏗 Architecture

frontend-web/ (Angular 19) ──┐
├──► backend/ (Node.js/Express) ──► MongoDB
frontend-app/ (Flutter) ──┘ API REST · OpenAPI · /api-docs

Un seul dépôt, trois applications. Les clients ne parlent jamais directement à la base, tout passe par l'API.

backend/

  • index.js — point d'entrée
  • openapi.js — le contrat (Zod + OpenAPI)
  • routes/users.js — routes
  • db.js / schema.js — MongoDB
  • scripts/ — génération des clients

frontend-web/ et frontend-app/

  • src/app/api/ — client TS généré
  • api_client/ — client Dart généré
  • Ne jamais éditer ces dossiers à la main

Chemin d'une requête backend :

requête → validateur OpenAPI → rate-limit → route → MongoDB
                 (400)              (429)         ↓
réponse ← validateur (vérifie aussi la réponse) ←┘
Le validateur vérifie les réponses aussi. Si le code renvoie quelque chose qui ne correspond pas au contrat → 500. C'est voulu : le contrat reste toujours vrai.

📄 Contrat d'API

C'est la pièce centrale. L'API est décrite une seule fois dans backend/openapi.js (Zod + openapi-zod-client). Tout découle de là :

backend/openapi.js
│ npm run clients:generate
├──► backend/openapi.json ← contrat JSON (versionné)
├──► frontend-web/src/app/api/ ← client TypeScript (Angular)
└──► frontend-app/api_client/ ← client Dart (Flutter)

Ce même contrat sert aussi à valider les requêtes et les réponses à runtime, à générer le Swagger UI, et à détecter les breaking changes sur les PR.

Modifier le contrat

  1. Modifie backend/openapi.js
  2. Écris la route dans backend/routes/ et ses tests
  3. npm run clients:generate dans backend/ (Java requis)
  4. Commite tout ensemble : code + openapi.json + clients régénérés
Conflit Git sur un fichier généré ? Ne pas résoudre à la main. Prendre n'importe quelle version, puis relancer npm run clients:generate.

Breaking changes

Sur chaque PR, oasdiff compare le contrat avec celui de main.

Cassant → CI échoue Non cassant → OK
Supprimer ou renommer un champ de réponse Ajouter une nouvelle route
Rendre un champ de requête obligatoire Ajouter un champ facultatif
Supprimer une route Ajouter un code de réponse (ex. 429)
Changer le type d'un champ Ajouter une valeur à une liste

Si la rupture est intentionnelle (tous les clients mis à jour dans la même PR) : ajouter le label breaking-change sur la PR. La détection est alors ignorée.

Utiliser un client généré

// Angular
private readonly health = inject(HealthService);
this.health.getHealth().subscribe(...)

// Flutter
final response = await ApiClient.instance.health();

Les noms de méthodes viennent des operationId du contrat : identiques des deux côtés.

Pattern mock / real

Les tests E2E du web (Playwright) et les tests d'intégration Flutter tournent deux fois :

ModeBackCe que ça prouve
mockSimulé — réponses prévues d'avanceLe client se comporte correctement
realVrai back, vraie base (construit depuis la PR)Client et API s'entendent vraiment
En mode mock, tout appel /api non simulé échoue avec 501 "Mock manquant" — plutôt que de passer silencieusement. Si tu vois ce message, il manque un arrange.mock dans ton test.

Règle d'équipe — Quand tu ajoutes une page ou un écran, tu ajoutes son test d'accessibilité.

Hook pre-commit

.githooks/pre-commit — activé par git config core.hooksPath .githooks. Formate automatiquement les fichiers du commit avant sa création. Comportements à connaître :

  • Ne touche que les fichiers stagés.
  • Si un fichier a des modifications non stagées, il les ignore et prévient.
  • Erreur de syntaxe → commit bloqué.
  • git commit --no-verify pour contourner exceptionnellement.
Le hook est un confort, pas une protection. La vraie garantie, c'est le check Format en CI. Le .gitattributes force les fins de ligne LF pour éviter que Windows casse le script.

CodeQL — comment réagir

  1. Cliquer sur « Show more details » dans la PR pour comprendre le vecteur d'attaque
  2. Corriger le code — l'alerte se ferme seule à la prochaine analyse
  3. « Dismiss » uniquement si c'est un faux positif documenté

Exemple concret : CodeQL a signalé l'absence de rate-limiting sur /users. Le correctif : 100 req/min par IP avec express-rate-limit, plus TRUST_PROXY=1 pour lire la vraie IP derrière nginx (sans ça, tous les visiteurs partagent la même limite).

🔀 Git & Pull Requests

Push direct sur main : interdit. Les règles de protection GitHub le bloquent de toute façon.

Branches

git switch main && git pull
git switch -c feature/SAE-42-pseudo-utilisateur

Convention proposée : feature/<ticket>-<description>, fix/, docs/, chore/. <ticket> = clé Jira.

Règles de protection de main

Configurées dans Settings → Rules du dépôt. La fusion n'est possible que si :

  • PR ouverte (no direct push)
  • 1 approbation d'un coéquipier (pas la sienne)
  • Tous les checks obligatoires sont verts :

Backend - test Front web - test E2E (mock) E2E (real) App - android build App - android e2e App - changes Contract - check Format - JS/TS Format - Dart + règle CodeQL

Si un workflow est renommé ou ajouté, cette liste doit être mise à jour dans les Settings, sinon la PR reste bloquée en attente d'un check qui n'arrive jamais (ou un check disparu ne bloque plus rien).

Modèle de PR

Le fichier .github/pull_request_template.md s'affiche à l'ouverture de chaque PR. Checklist : description + ticket Jira, tests passent, formatage fait, clients:generate si contrat modifié, label breaking-change si cassant, capture d'écran si l'interface change.

Relecture

  1. Vérifier que la CI est verte avant de commencer
  2. Le code fait-il ce que la PR annonce ? Les cas d'erreur sont-ils testés ?
  3. Si le contrat change : clients régénérés ? changement cassant justifié ?
  4. Si l'interface change : test d'accessibilité présent ?
  5. Aucun secret, aucun fichier de debug oublié

Garder sa branche à jour

git fetch origin && git merge origin/main

Sur un conflit dans un fichier généré (openapi.json, api/, api_client/) : prendre n'importe quelle version, puis relancer npm run clients:generate.

⚡ CI (GitHub Actions)

Les workflows sont dans .github/workflows/. Sur un push, ils ne se déclenchent que si leurs fichiers surveillés ont changé. Sur une PR, ils se déclenchent toujours (nécessaire pour les checks obligatoires).

Ce qui se passe sur une PR

push → Backend - test Front web - test E2E (mock/real) App - android build App - android e2e Contract - check Format - JS/TS Format - Dart CodeQL → tout vert + 1 approbation → fusion

Lire un échec

Dans la PR → section Checks → Details à côté de la croix rouge → ouvrir l'étape en rouge → les dernières lignes contiennent l'erreur.

failed to connect to the docker API Docker Desktop pas lancé Lancer Docker Desktop, attendre qu'il soit prêt

UnsupportedClassVersionError pendant clients:generate Java 8 (trop ancien) Installer JDK 17+ ; vérifier java -version

Format - Dart rouge alors que dart format a été lancé Mauvaise version de Flutter Aligner sur Flutter 3.47.6, relancer dart format
« Mock manquant » (501) dans Playwright Route non simulée en mode mock Ajouter la réponse simulée dans arrange.mock
Playwright : Executable doesn't exist Chromium non installé npx playwright install chromium dans frontend-web/
Playwright mode real ne démarre pas le back backend/node_modules absent npm install dans backend/
Couverture sous le seuil Code non testé Ouvrir backend/coverage/lcov-report/index.html, écrire les tests manquants
Hook de formatage silencieux Hook non activé ou non exécutable git config core.hooksPath → doit afficher .githooks ; Linux/macOS : chmod +x .githooks/pre-commit
PR bloquée en « Waiting for status to be reported » Check obligatoire introuvable (workflow renommé ou supprimé) Comparer la liste dans Settings → Rules avec les noms réels des jobs
PR Dependabot rouge Mise à jour incompatible Ne pas fusionner — lire l'erreur ou fermer la PR
